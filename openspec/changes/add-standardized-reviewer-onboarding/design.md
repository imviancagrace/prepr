## Context

See proposal.md for motivation. The original implementation added standardized reviewer packages, local acceptance, inline setup preparation, and runtime enforcement. Profiles retain local paths or pinned GitHub sources, while runtime loads accepted effective packages. Setup's keep mode preserves YAML bytes. These completed parts remain in place.

Follow-up testing at Prepr main `7b366f3` exposed mandatory 30-second readiness probes that start ordinary launcher sessions in the project environment. The implementation waits for process exit before parsing output, so a successful response followed by a hanging hook still fails. The final report assumes comparison exists even after an earlier failure. The follow-up removes readiness AI sessions and introduces shared static checks and human prerequisite confirmation for Claude and Codex. Token/cost figures and the tester's exact launcher configuration were not independently verified.

This design spans onboarding, setup, runtime resolution, and evidence output. The existing rule against a default review prompt remains: shared formatting is an interface, and code-review judgment still comes entirely from the chosen reviewer. Reviewer acceptance and prerequisite confirmation are separate local decisions; neither is a per-run scope approval.

## Goals / Non-Goals

**Goals:** Faithful, inspectable adaptation; one project-local acceptance per effective reviewer version; no modification of original/global skills; consistent review/debate output; safe migration of raw references; shared Claude/Codex prerequisite checks and confirmation without extra AI sessions; useful failure reports before comparison exists.

**Non-Goals:** A generic converter for every agent skill, automatic semantic-fidelity certification, marketplace publication, shared review criteria, reviewer default selection, cross-user approval distribution, signatures/identity infrastructure, or background conversions during reviews.

## Decisions

### 1. A versioned reviewer package, with judgment separate from transport

Version 1 contains `reviewer.json`, a rendered `SKILL.md`, and only the retained reference files needed for review. Structured reviewer content covers priorities, methods, evidence standards, communication, native severity definitions, and optional substantive assessments. Each section can explicitly state that the source defines no rule; the adapter must not invent a generic checklist. `SKILL.md` is rendered deterministically from validated content plus the shared runtime boundary and output contract. Validation checks that the render matches, referenced paths stay within the package, declared resources have explicit access/limitations, and the version is supported. No bundled executable scripts or indirect original-skill invocation are permitted.

The common initial result contains `overview`, `verification`, and `findings`. Findings preserve native wording, rationale/evidence, known file/line, optional native severity, and assessment kind (asserted issue, question, or hypothesis). An explicit issue/no-issue verdict is optional when unknown and must not be guessed. Support a dedicated question field or equivalent preserved content and optional reviewer-specific assessments such as spec alignment with evidence. Map this envelope to existing normalized finding/verification structures without forcing questions into confirmed bugs. Debate uses the current explicit stance/verdict/correction/confidence/duplicate-ID contract.

Severity mappings remain explicit local profile choices, not converter guesses. A common envelope adds no review checklist and does not homogenize Vee's questions into prescribed fixes. Legacy transcript normalization remains useful for historical reports and nonconforming model output, but is not a reviewer-onboarding bypass.

Alternative: add only a frontmatter marker. Rejected because a marker cannot establish content compatibility or acceptance. Alternative: make all reviewers use one common checklist. Rejected because it defeats independent standards.

### 2. Source inspection and semantic extraction run in the invoking assistant

Add `skills/prepr-prepare-reviewer/SKILL.md`, supported by a format/template reference and deterministic inspect/validate/preview/accept helpers. The same preparation procedure is used standalone or inline by setup. During setup the invoking assistant performs extraction within its existing conversation; no nested reviewer/model-probe session is started. Ship the preparation resources with setup in a self-contained distribution or explicitly bundle both skills together with verified resource lookup; do not depend on the user having separately installed an optional global skill. Keep one authoritative format/validator in the workflow package, accessible from fresh remote main and reusable by onboarding helpers.

Read source `SKILL.md` and explicitly relevant linked references as data, tracking what was read. Do not execute startup scripts, follow instructions to publish, or recursively traverse unrelated links. Local sources retain their actual identity and source-relative resolution; GitHub sources retain repo, immutable commit, and path. Source paths are inspectable input, not permission to broaden reads. Resolve symlinks/path escapes explicitly rather than silently copying external content.

Classify material source sections as retained, excluded, or unresolved, with source file/section references and reasons. Preserve domain standards, baseline reasoning, priorities, voice, and substantive dependencies. Remove scope/checkout ownership, PR discovery/publication, installation, scheduling, and extra-reviewer orchestration. For Vee this keeps spec-first assessment, review order, baseline classifications, redundancy checks, and concise questions; it excludes the default-agent pass and preparation/publication procedures. If a source combines those concerns inseparably, leave a draft and ask a focused clarification. No automatic rewriting of the original and no claim that schema validity proves faithful extraction.

### 3. Dependency declarations distinguish review rules from runtime facts

Retained review-standard documents are copied into the candidate as attributed, versioned snapshots when authorized and practical, or pinned to immutable readable sources. Include their contents/fingerprints in provenance and acceptance. Preserve relative links through explicit rewriting; never leave an adapted package pointing into a temporary clone. An external mutable standard without a verifiable revision remains unresolved until it can be captured or otherwise checked. Do not copy private standards into tracked project files.

A resource needed only as runtime evidence or data is declared separately with required/optional status and permitted read access. Its changing data is not a change to the reviewer's standards. Actual review sessions establish runtime access; no separate model session probes it. A required runtime resource that cannot be read leaves the affected assessment blocked/incomplete, while optional missing evidence remains an explicit limitation. Do not describe user confirmation or host access as observed reviewer access. An essential unreadable review standard still blocks acceptance. Do not drop authenticated resources merely to make preparation pass, and do not treat source instructions as tool-installation or credential authorization.

### 4. Draft, preview, explicit acceptance, then activation

Use local `.archon/prepr-reviewers/drafts/<id>/` for candidates, `.archon/prepr-reviewers/accepted/<digest>/` for immutable accepted packages, and a local registry/acceptance ledger under `.archon/prepr-reviewers/`. Exclude draft/private content and approval state from new Git tracking; preserve the existing bundled peer folder and unrelated files. A downloaded ready-made package or acceptance record from another machine is not local human consent.

Deterministic preview outputs the exact candidate digest, readable effective instructions, retained/excluded summary, dependencies, limitations, and blockers. The assistant asks the human to accept, edit, or reject that concrete version, then waits. Only after an explicit matching human answer may the acceptance helper validate the same digest and register it. Invoking setup, choosing a reviewer, keeping a YAML file, an auto-generated `accepted: true`, or silence is insufficient. Helpers record a local event only when called through this approved operation; they do not claim cryptographic proof of human identity.

Reject unresolved material ambiguities or essential missing standards before acceptance. Edits regenerate the preview and invalidate pending approval. Declining or leaving the prompt unanswered leaves a draft; a failed activation restores prior registry/configuration state. Previously accepted package versions remain recoverable. Registration activates a version only; it never starts a workflow.

### 5. Exact-content reuse and conservative invalidation

Bind records to format/output-contract version, source identity, source `SKILL.md` and inspected instruction-reference hashes, effective instructions/render, retained standards, and dependency declarations. Separate volatile preparation timestamps and presentation-only summary formatting from execution fingerprints. Changes to launcher/model selection alone do not rewrite review standards or invalidate reviewer acceptance; they require renewed prerequisite confirmation under decision 8.

For version 1, conservatively require revalidation and renewed acceptance for changed bytes in source instructions or retained standard content, even when an edit might be cosmetic; never attempt an automatic semantic-equivalence proof to carry approval forward. Files outside the explicitly inspected instruction set do not invalidate approval merely because an unrelated repository commit changed. A new pinned reviewer source revision is a new source identity and needs preparation. A source that cannot be verified blocks use; do not silently run a stale accepted adaptation. Hashes identify inspected content; they do not prove that the assistant discovered every implicit dependency, so disclose extraction coverage.

Already standardized and locally accepted content is reused without conversion or prompts. A new standardized package needs validation and the same first acceptance. Relocation requires an explicit relink of source identity with content checks; no implicit authorization to read different resources. Contract-version changes invalidate incompatible records. Tests use explicit fixture acceptance records constructed in disposable projects, never a production auto-approve flag.

### 6. Preserve profile references while enforcing effective-package resolution

Keep the profile's existing `skill` reference as source identity so keep mode can preserve configuration bytes. Store the mapping to accepted effective packages in the local registry. Direct skill references resolve through the same mapping; selecting an accepted package directory itself still requires matching local acceptance, preventing a path-based bypass. Bundled peer is shipped in standard form but receives local acceptance like any other reviewer.

Use bounded, read-only inspect/fingerprint operations reusable by setup and runtime. Before either actual review, resolve both sides, check matching supported acceptance and content, validate static prerequisites and matching confirmation, and pin effective package snapshots for the run. Recheck packages before initial review so a concurrent edit cannot slip through a validated record. Sessions load only the accepted package and its retained references as reviewer-specific instructions, never the raw source as instructions. The original source may be read as provenance by preparation/checks, not as a second instruction set. Agent prompts contain Prepr scope/operation boundaries and the structural output/debate envelope plus the accepted reviewer-specific content. Removing probes does not isolate the launcher's own hooks, plugins, or project context; that remains a distinct operational limitation.

A missing/stale/unaccepted side stops both reviewers with `prepr-prepare-reviewer` or setup guidance. Normal runs do not convert, prompt, register, install, or mutate YAML/acceptance state. Scope-only preview retains its existing bypass. Effective package digests, source revisions/hashes, format version, and local acceptance references enter complete JSON evidence; credentials and full private source documents do not. No report filename, artifact pointer, debate-session count, or duplicate-reuse semantics change.

Setup inspects compatibility after the user selects or keeps the pair. Automatically prepare missing candidates inline, then pause for each new effective version's explicit acceptance (a combined preview can cover both if the human explicitly accepts both named digests). Human acceptance copies the exact package to `.archon/prepr-reviewers/accepted/<digest>/` and updates the ignored registry. Already standardized but unaccepted packages still need local acceptance; unchanged accepted versions reuse existing records.

Source installations should follow Archon's documented UI build instructions when needed; do not add a build step to every Prepr setup. ### 8. Shared prerequisite confirmation replaces readiness model probes

Setup performs bounded, non-model checks for Git, Bun, supported Archon and selected launcher executables/versions, installed workflow integrity, local profiles, accepted reviewer packages, and effective launcher/model compatibility. Install missing prerequisites only under the existing user-approved installation plan. Resolve each effective model, including Archon's configured large tier, without starting a model session or changing credentials.

After showing static results and effective selections, ask the human to confirm they are logged in to each selected launcher and can use the named models. Record explicit confirmation in separate project-local, Git-excluded setup state tied to the canonical project, local scope marker, launcher identity and resolved model selections. Do not store tokens, credentials, or copies of authentication files. Keep this record separate from reviewer acceptance and from kept YAML bytes. Preserve previous active configuration/records if confirmation is declined, unanswered, or a staged replacement fails. Setup completes only with passing structural checks, accepted reviewers, and matching prerequisite confirmation; actual access remains unproven until use.

Reuse matching local confirmation without a per-run prompt. Launcher/model changes, including resolved tier changes and launcher/model overrides, require setup confirmation for the new selection. Another project's or machine's record is not local confirmation. A login that expires after confirmation is detected by the actual reviewer session; the record is an attestation, not an authentication test. Ordinary runs never prompt, install, authenticate, convert, or record new consent. Legacy installations without confirmation rerun setup; valid existing reviewer acceptances remain reusable.

Before either initial reviewer starts, validate both selections and static prerequisites plus matching confirmation. Do not run readiness AI sessions, add a probe-timeout workaround, switch accounts/models/launchers, use API-key-only bare mode, or silently broaden permissions. Then start the two independent actual reviews under their selected native launchers. Authentication/model failures or timeouts remain operational failures with side, launcher, effective model, available evidence, and actionable recovery guidance. The other side may already have started; never claim both sessions were prevented once actual startup began. Decision 12 adds prompt cancellation of that sibling after a fatal execution failure rather than waiting for both sides to finish. Existing read-only boundaries and bounded review timeouts remain.

Alternative: increase or configure the readiness timeout. Rejected because it retains duplicate model calls and startup overhead. Alternative: isolate readiness with launcher-specific flags or finish a probe on early JSON. Removing probes cannot guarantee hook-free actual reviews or cheap model execution.

### 9. Reports survive failures before comparison

### 13. Concise Markdown over complete audit evidence

The previous evidence-preservation correction remains necessary, but the normalizer's full output is not the Markdown layout. JSON retains every supplied check, assessment, limitation, original response, snapshot identifier, operational check and cancellation event. The later successful UX Scorer run `6f0c552f-a62c-426e-9211-420907312acb` demonstrated remaining presentation drift: about 1,970 words for two files, 13 preliminary verification/assessment bullets, repeated qualifications, and shared uncertainty labeled as disagreement. This refines presentation without changing the reviewer contract or debate engine.

The approved default Markdown order is:

- Outcome/support and open-question counts, resolved reviewer names and selected scope. Operational failure or a material scope/coverage blocker qualifies the opening immediately.
- **Reviewer differences and where they landed:** substantive opposing assessments, changes/corrections during discussion, and concerns initially raised by only one reviewer even when later accepted. Each short entry identifies the initial attributed positions, the material discussion change and the final position or remaining disagreement. Resolved differences stay here rather than repeating under agreements.
- **Open questions requiring evidence:** unanswered questions/hypotheses without established opposing verdicts. State who raised the question, the other reviewer's observed response and the specific missing evidence. Shared uncertainty is not disagreement or proof of a defect. A genuine incompatible-position concern stays in the differences section with its uncertainty rather than appearing twice.
- **Other agreements:** supported concerns without a material reviewer difference. Related findings may share a short presentation block with an explicit member count, without semantic consolidation.
- **Material review limits:** concise attributed tests and coverage/access/snapshot/data limitations that affect confidence or interpretation. Omit empty sections; omit routine withdrawn entries and retain their records in JSON, optionally with one short dismissal count. A substantive disagreement ending in dismissal remains visible in the differences section when needed to explain the result.

Build this narrative from saved initial findings and original-session debate positions. A reviewer who did not initially flag a concern is not recorded as opposing it; an incomplete initial review is not evidence that its author overlooked or dismissed it. Distinguish issue/no-issue assessments, unknown verdicts and configured comparable urgency differences. Explain the recorded change leading to the final outcome instead of replaying every round. Preserve a question-led reviewer's question and do not manufacture a prescribed fix, generic decision bullet or reviewer opinion. Use named, flexible labels such as Initially, Discussion and Final position; the old mandatory Review conclusion/Why the conclusion changed/What you need to decide labels no longer constrain the default layout.

Presentation grouping never changes normalized concern membership, verdicts, IDs, support/open counts or the bilateral duplicate-confirmation/reuse rules. Keep unresolved or contradictory members visible in their appropriate section; a supported neighbor cannot confer confirmation. A group showing two related supported findings still contributes two to the outcome count and leaves both JSON records intact. Use the latest supported correction for the actionable concern text so a withdrawn portion is not repeated as a current defect; keep that change's attribution where it explains a reviewer difference.

Native ratings are optional and belong to their author. No accepted package or consent record needs to change.

Replace verbose audit-shaped paragraphs with compact evidence-based entries, retaining the condition or qualification needed to understand each outcome. A limitation keyword must not exempt an entire paragraph from shortening, and extracting a qualification must not print it again as a second reasoning bullet. Keep substantive assessments in Markdown only when they change the decision; full assessments, routine missing-ticket/score explanations, hashes, provenance, setup history, file-read narratives and round-by-round reasoning remain in JSON. Do not hide failed checks, blocked required evidence or snapshot substitution; do not combine overlapping focused-test counts, imply a passing full suite or truncate away a condition. ### 14. Review scope excludes managed tooling independently of Git state

Use one explicit path-based review-target policy across normal and preview capture, local and committed branch diffs. Exclude the installed `.archon/workflows/prepr/` subtree, `.archon/prepr-reviewers/`, Prepr's local profile/provenance/prerequisite-confirmation files, backups and staging state, and known Archon-generated artifact/report, log and cache locations. Identify generated locations from documented layout or the actual run configuration, including the run artifact directory when it is inside the target checkout. Match normalized repository-relative paths against those bounded locations; do not infer exclusions from file-name substrings, another user's machine paths or instructions found in reviewer/project content. Unrelated authored workflows and application files remain eligible. Never blanket-exclude `.archon/`, every ZIP, or the unrelated `.ux-runs.zip` archive.

Apply the policy regardless of whether entries are staged, unstaged, untracked, tracked or committed. Enumerate eligible paths before reading untracked payloads or constructing Git patches. Filter patch entries, content snapshots, file lists, statistics, diff sizes and local-snapshot fingerprints consistently before saving review snapshots or producing launcher inputs. Handle renames, deletes, binary files and unusual path names without exporting excluded-side content or suppressing an eligible-side change. Changes confined to excluded tooling do not invalidate an otherwise unchanged eligible local snapshot. Both reviewers and scope-only preview receive the same eligible project scope. The scope filter governs review targets, not the separate loading of approved effective reviewer instructions and permitted runtime evidence. Accepted packages remain available even inside excluded state directories. Reviewers must not count those instructions or operational artifacts as changed project code or expand the supplied scope to audit installation files. Keep immutable reviewer provenance and existing acceptance gates unchanged.

Filtering does not replace literal-data-safe debate transport. Eligible application files can also contain `$node.output`-style strings. Regressions must carry such text through actual include/fan-out expansion without interpreting it, while retaining complete raw evidence and original sessions. Do not rely on filtering Prepr YAML to hide the orchestration bug.

## Risks / Trade-offs

- Semantic extraction may lose meaning: provide source-linked summaries, block material ambiguities, and require human inspection; test contrasting representative reviewers rather than only checking JSON shape.
- Conservative hashes can repeat approval for cosmetic instruction edits: state this version-1 policy clearly; improving semantic reuse is outside this change.
- Existing raw-reference users will encounter a new preparation requirement: document the breaking migration and retain source references/old configuration while onboarding.
- Private domain references can be unavailable or unsuitable for copying: retain access declarations and block essential unknown standards; no automatic credential changes.
- Local acceptance records are mutable local state: validate digests and keep records outside repository-supplied instructions; do not claim protection against an actor who can freely modify the user's trusted local state.
- New schema can flatten reviewer voices or imply defects from questions: preserve native text/assessments and test explicit unknown verdicts and severity mappings end to end.

- Prompt cancellation can race with natural completion: preserve the first failure and actual sibling outcome; test simultaneous failure, already-finished siblings and process cleanup without affecting other runs.
- Concise Markdown can hide material uncertainty: keep complete JSON evidence and require regression examples for partial review, failed debate, snapshot access, test status and actionable limitations.

- Tooling exclusions can accidentally hide authored work: use bounded managed/generated path rules, cover rename/path-boundary cases and expose exclusion metadata; keep unrelated archives and workflows eligible.
