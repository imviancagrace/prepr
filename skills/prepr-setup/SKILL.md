# Prepr setup

Set up the chosen project using `https://github.com/imviancagrace/prepr.git`, branch `main`. Never use an author's checkout or a stale cache instead of fetching main. This skill only prepares setup: never start an Archon workflow, including preview-only, reviewer, debate, or model-probe sessions. Use only bounded static prerequisite checks; never launch a readiness AI session. Never publish to GitHub or change repository visibility.

## Select and inspect

Identify the intended project; ask if ambiguous. Resolve its Git root before project writes. If Git is missing, obtain the intended path first and verify the root after approved bootstrap.

Inspect `.archon/prepr.local.yaml`. Whenever it exists, ask **keep the existing configuration or configure a new pair?** Keep means byte-for-byte preservation; invalid kept configuration stays unchanged and is reported incomplete. For new configuration, ask for two skills, display names, native launchers (`codex` or `claude`), and model settings. Both reviewers may use one launcher. Do not assume Vee exists or choose a pair for the user. The peer-review-guidelines skill bundled in remote Prepr is an optional choice (`bundled:peer`). Accept local SKILL.md/directories or the existing immutable `github:owner/repo@<40-character-commit>:path` form. Resolve user-supplied paths safely; do not execute a skill's startup instructions.

Preserve optional explicit severity mappings and required read declarations; don't guess either. Keep unrelated profiles and settings when replacing a pair. If new profile IDs collide with unrelated profiles, ask before overwriting them or choose unused IDs.

## Prepare prerequisites with permission

Read [prerequisites.md](references/prerequisites.md) for the detected platform. Check Git, Bun, Archon >=0.11.1, selected launcher(s), and tools needed by the chosen install method or declared dependencies. Before Bun exists use ordinary `command -v`/`--version` shell checks. Do not install the unused launcher or project application dependencies.

Show missing/outdated tools, proposed commands and machine changes, then ask permission. Wait for an actual answer. Run only the approved plan and verify each result; preserve compatible installations. A changed plan, including a new package manager, needs new permission. Interactive logins belong to the user; never request or write credentials. Recheck non-model status commands afterward. Failed or declined prerequisites mean incomplete setup.

Before Bun is available, run `sh scripts/inspect.sh <codex|claude> ...` from this skill folder for nonmutating bootstrap checks. Unsupported platforms must use the documented manual path. After Bun is available, use `scripts/setup.ts inspect <project> <launcher,...>` for bounded tool/version checks. Never silently modify global Archon tiers. Omit a profile model only when `archon ai tier list --json` shows a matching large-tier provider; otherwise obtain a compatible explicit model from the user. Static checks do not establish model entitlement.

## Fetch and install

Read [helper.md](references/helper.md). Run the helper from this installed skill's directory, using absolute paths and shell-safe argument quoting. It imports the fetched package's pure profile-selection function to avoid a second schema implementation; main must include the setup-compatible export. An older main fails with instructions rather than bypassing validation.

1. Fetch remote main with `fetch`; keep the returned staging path for this invocation. Authentication failure stops installation without fallback.
2. Inspect existing workflow differences with `plan`. If content differs, show changed files and ask **keep or replace the workflow?** This choice is separate from keep/new reviewer configuration. Reuse identical files. Bundled reviewer sources are versioned and inactive; do not overwrite a modified versioned source.
3. Onboard both selected reviewers before configuration activation. Read `skills/prepr-prepare-reviewer/SKILL.md` and its `references/format.md` from this exact fetched checkout and follow them inline in this conversation; these resources ship with Prepr main, so no separately installed global skill is needed. Check current accepted packages first and reuse unchanged versions. For `bundled:peer`, run `stage-bundled <project> <source>` to materialize a versioned inactive local source; preserve any existing peer source. Then prepare its concrete candidate like any other reviewer. Ask the human to accept/edit/reject the shown instructions, exclusions, dependencies, limitations, and digest. Keep/new YAML choice is not reviewer acceptance. Never start a nested reviewer/model session. A decline or unanswered acceptance leaves setup incomplete and the old active pair unchanged.
4. Prepare a temporary JSON request capturing the actual choices. A new profile uses a YAML file staged outside the project. Do not copy credentials into either file. Include each explicitly accepted new candidate as `{id,digest,decision:"accept"}` in `acceptances`; do not call standalone registration early. Helper validation preserves unrelated settings and commits accepted mappings/configuration together, with recoverable backups. Kept YAML bytes stay unchanged even when onboarding updates separate ignored registry state.
5. Run `preview <request.json>` to show static check results, the exact resolved launcher/model selections and confirmation digest. If it reports `confirmation-required`, ask the human to explicitly confirm they are logged in to these launchers and can use these models, then wait for a separate answer. This is independent of reviewer acceptance and installation permission. Choosing keep/new, accepting reviewers, invoking setup, or silence does not confirm prerequisites. If declined/unanswered, stop incomplete and preserve the prior configuration. After explicit confirmation add `confirmation: {digest: SHOWN_DIGEST, decision: "confirm"}` to the request. Unchanged matching local confirmation is reused without a new prompt; launcher/model changes (including resolved tier changes) require renewed confirmation. Never create confirmation automatically or store credentials. A preview alone does not activate reviewers or replace configuration.
6. Use `apply` only after choices are answered. It writes the workflow, optional selected bundled reviewer, local profile/provenance, and local Git excludes; no commits or index edits. If the profile is already tracked, stop and ask for remediation; do not silently untrack it. Do not treat an ignore rule as untracking.
7. Use `verify <project> <source>` with the same fetched source for static setup checks, including retained older installations. Do not invoke any workflow to resolve uncertainty. Clean up fetched staging and request files after reporting, leaving project backups available.

A kept workflow has its existing verified revision or unknown provenance, never the newly fetched revision if it differs. Failed updates restore prior content; report backup paths and any incomplete cleanup. Preserve unrelated workflows. Do not execute reviewer instructions or arbitrary fetched scripts. The helper uses the fetched Prepr package’s profile and standardized-reviewer validators; prerequisite installers require the explicit approval above.

## Finish with commands, never execution

Report complete/incomplete, actual project/config paths, installed source SHA, retained/updated content, prerequisite actions, backup paths, accepted reviewer versions or pending acceptance blockers, and blockers. Explicitly distinguish static setup checks from unknown runtime login, model availability, reviewer sandbox access, or project test results. Report static facts and saved user confirmation separately. Confirmation attests to login/model access; it does not prove current authentication, model entitlement or reviewer resource access. Actual user-started review sessions establish runtime behavior, with no separate readiness AI session. Expired login/model failures produce an incomplete report and recovery guidance. Actual sessions can still inherit user hooks/plugins/context and may time out.

Provide the helper's safely quoted `cd` and workflow commands for local review, committed branch review, and local/branch previews. Explain that local selects staged/unstaged/nonignored untracked work; branch requires a clean checkout. Installing workflow files can itself create local changes. If incomplete, label the commands for use after blockers are resolved. Never execute these commands automatically.


Also display `archon serve` as the optional manual command to start the Archon web UI in a separate terminal. It runs in the foreground on port 3090 by default; binary installations download matching UI assets on first use. CLI reviews do not require the UI. Do not start the server, download UI assets, or chain review commands behind the foreground server. For source installations, point to Archon's documented UI build instructions when needed: https://archon.diy/reference/cli/#serve.

Existing installations without prerequisite confirmation must rerun setup. Reuse unchanged accepted reviewers and preserve kept YAML bytes; add confirmation separately under `.archon/prepr-prerequisites.json`. A normal run does not prompt or repair setup. Setup handles inline transformation automatically; users supply reviewer paths/references and need not run the preparation skill separately or copy files into a special folder. Drafts and accepted copies are saved automatically under the target project's `.archon/prepr-reviewers/`.
